## 1. Summary

The newer systems are in good shape. Gold (`services/gold.ts`), Talers, shops, husbandry, workstations, tanning, trapping, buffs and fishing bait all use transactions and row locks correctly, and the July fixes held: socket auth, CORS, rate-limit ordering, JWT fail-fast, trade accept atomicity and the ground pickup gate are all still sound.

The problems cluster in the **older code that predates the transaction rule**. The same bug appears over and over: read a row, decide, then write an absolute value or a blind add, with no lock. Two requests sent at the same moment both pass the check and both write. Five of those are live item duplications that anyone with a browser console can trigger today.

The second cluster is **the game tick**, which has no step that claims an action before resolving it. That is safe only while every tick finishes inside two seconds, PM2 runs exactly one process, and no resolve path throws after granting something.

## 3. Critical: item duplication

All five share one root cause and one fix shape: do the read and the write inside one transaction, lock the row you read (`forUpdate()`), and write relative to the locked value. Section 5.1 turns that into one module so the pattern cannot be skipped again.

### C1. Unequip duplicates the worn item **[PROVEN]**
`routes/equipment.ts:279`. The equipment row is read **outside** the transaction, then the transaction adds that item to the pack and clears the slot. Two simultaneous unequips both see the item in the slot and both hand it back.

Harness: one hatchet worn, five parallel `POST /api/equipment/unequip` → two returned 200, **pack held 2 hatchets**.

**Fix:** inside the transaction, `trx('player_equipment').where({ player_id }).forUpdate().first()`, read the slot from that row, and bail if it is already empty.

### C2. Equip swaps a cheap item for a copy of the worn one **[PROVEN]**
`routes/equipment.ts:125`. Same shape: `currentItemId` is read outside the transaction, so two concurrent equips both return the worn item to the pack. Only one of the two incoming items ends up in the slot, and the other is consumed and lost.

Harness: wearing a hatchet, holding one more hatchet and two Cheap Axes, two parallel equips of the Cheap Axe → **hatchets 2 → 3, Cheap Axes 2 → 1**, every run. Repeatable, so any valuable worn item can be farmed by feeding it cheap items of the same slot.

**Fix:** as C1. Lock the equipment row first and read `currentItemId` from the locked row.

### C3. Storage withdraw and deposit duplicate whole stacks **[PROVEN]**
`services/property.ts:82` (`depositItem`) and `:125` (`withdrawItem`). No transaction, no locks, and the source row is either deleted or set to an absolute `quantity - qty` computed from a stale read. Every parallel request passes the check, the delete succeeds harmlessly as a no-op after the first, and every request adds the full amount to the destination.

Harness, five parallel requests of a 100-stack:
- Withdraw: **100 → 300**
- Deposit: **100 → 500**

**Shop storage uses these same two functions** (`routes/shops.ts:326` and `:334`), so the hole covers shops as well as farmsteads.

**Fix:** one transaction, `forUpdate()` on both the source and destination rows, and a conditional decrement (see §5.1).

### C4. Ground drop duplicates whole stacks **[PROVEN]**
`routes/groundItems.ts:45`. Reads the inventory row, deletes or decrements it, then inserts the full `dropQty` on the ground. Nothing ties the insert to the delete having actually removed anything.

Harness: five parallel drops of a 100-stack → **500 on the ground**, pack empty. Drop requires a trusted account, but that is every registered player.

**Fix:** one transaction with a locked inventory read, or `removeItemFromInventoryWithin` from `services/inventory.ts`, which already does this correctly. Insert the ground row only when the remove returns true.

### C5. Kiln load pays for two burns with one set of logs
`services/smithing.ts:49` (`loadKiln`). The "kiln already burning" check, the log consumption and the `kiln_jobs` insert are separate statements with no transaction. Two parallel loads both pass the check, both consume from the same stale stack read (a full-stack delete is a no-op the second time, and a partial `decrement` goes **negative**), and both insert a job. Each job is collected in turn, so the Charc is doubled.

Not run in the harness, but it is the same shape as C3 and C4.

**Fix:** transaction; lock the player row (or the log stacks) first; re-check the active-job condition inside; add a partial unique index on `kiln_jobs (player_id, location_id) WHERE is_collected = false` as the database-level guard.

## 4. Findings by severity

### High

**H1. Bans, mutes and password resets do not end existing sessions.**
`middleware/auth.ts` verifies the JWT signature and nothing else. Login refuses banned accounts (`routes/auth.ts:150`), but tokens last **30 days** and `requireAuth` never checks `is_banned` or `banned_until`. The ban route's `force_logout` emit is a courtesy to a cooperative client. A banned player with a saved token keeps trading, chatting and playing, and their tick actions keep resolving. The same gap means a password reset (after an account compromise) leaves the attacker logged in.
**Fix:** add `players.token_version` (int, default 0) and put it in every token. `requireAuth` compares it and checks the ban columns. That costs one indexed lookup per request; a 30-second in-process cache keyed by player id makes it effectively free. Bump the version on ban, password change, password reset and a new "log out everywhere" button. Check it in the socket handshake too.

**H2. The game tick has no claim step.**
`services/gameTick.ts:154`. `setInterval(async …, 2000)` reads every action with `completes_at <= now`, then resolves them one by one. Nothing marks an action as taken before resolving it. Three ways that goes wrong:
- **Overlap.** `setInterval` does not wait for the previous async callback, so a tick that runs past two seconds (a burst of completions, feat evaluation on level-ups, the guest sweep, a slow query) starts the next tick on the same rows, and both resolve them. Double items, double XP.
- **Two processes.** If PM2 ever runs this in cluster mode or with two instances, every action resolves twice. There is no `ecosystem.config` in the repo, so this depends on however it was started on the box.
- **Retry loop.** `processCompletedAction` catches every error and leaves the row untouched. Any throw *after* the resolve granted something and *before* `completes_at` moves (a missing skill row making `relevantSkill.id` a TypeError, a failure in `emitActionComplete`) re-resolves the action on the next tick, every two seconds, until someone notices.

**Fix:** claim atomically before resolving:
```sql
UPDATE player_actions
   SET completes_at = now() + interval '5 minutes'   -- lease
 WHERE id IN (SELECT id FROM player_actions
               WHERE completes_at <= now() AND bot_check_pending = false
               ORDER BY completes_at
               LIMIT 200
               FOR UPDATE SKIP LOCKED)
RETURNING *;
```
The lease means a crash mid-resolve retries once after five minutes, not every two seconds. Add a module-level `ticking` flag so a slow tick is skipped rather than overlapped, and pin PM2 to one fork-mode instance in a committed `ecosystem.config.cjs`. §5.2 covers the larger refactor this enables.

**H3. Quest rewards pay once per parallel request.**
`routes/npcs.ts:175` (`complete_talk_objective`) and `routes/quests.ts:148` (`checkQuestCompletion`). The talk objective is read, marked complete and then `checkQuestCompletion` runs, with no lock. `checkQuestCompletion` itself sets `status: 'completed'` **unconditionally** (line 164) and pays rewards regardless of the previous status. Fifty parallel "hand in" clicks pay the gold, items and XP fifty times.
**Fix:** make completion the gate. `UPDATE player_quests SET status='completed' … WHERE player_id=? AND quest_id=? AND status='active'` and pay rewards only when that update reports exactly one row. That single change makes every caller idempotent.

**H4. Negative trade offers take items from the partner.**
`routes/trades.ts:182`. `/offer/item` never validates `quantity`. An offer of `-50` passes the "do you have enough" check (`have < -50` is false), and at accept `decrement('quantity', -50)` *adds* 50 to the offerer while `increment(-50)` removes 50 from the partner, or inserts a negative inventory row. It needs the victim to accept, so it is a scam rather than a silent dupe, but the client may not render a minus sign clearly, and negative rows break every downstream check. Floats and numeric strings also reach the column (`existing.quantity + "5"` concatenates).
**Fix:** `const qty = Math.floor(Number(quantity)); if (!Number.isInteger(qty) || qty <= 0) 400`, mirroring `/offer/gold`. Validate again at accept.

**H5. Trade offers can change underneath an accept.**
`/offer/item`, `/offer/item/remove` and `/offer/gold` update the offer and reset both acceptance flags **without** taking the trade row lock that `/accept` takes. If B changes the offer at the same moment A accepts, A's transaction can read B's old acceptance flag alongside B's new offer and complete a trade A never saw. That is the classic bait-and-switch.
**Fix:** every offer mutation runs in a transaction that locks the `trades` row first. Better still, give `trades` an `offer_version` column that every mutation bumps; the client sends the version it displayed with `/accept`, and the server refuses a mismatch. Also add the missing party check on `/offer/item/remove` (noted in the code's own comment).

**H6. Selling into a shop can destroy the seller's goods.**
`services/shops.ts:726` (`sellToShop`). Knex **commits** a transaction whose callback *returns*; only a *throw* rolls back. `sellToShop` removes the seller's items, then returns `{ success: false }` if the shop's fund cannot cover the payment (line 782) or its storage is full. Both returns commit the removal with no payment. Full storage is an ordinary state for an active shop.
**Fix:** move both checks above `removeItemFromInventoryWithin`, and adopt the rule everywhere: inside `db.transaction`, failure paths **throw** a typed error (the `TradeAbort` pattern in `routes/trades.ts` is the model). Add that rule to CLAUDE.md §5; nothing in the codebase flags it today.

**H7. Merchant daily allowances can be exceeded with parallel requests.**
`routes/marketplace.ts:281` (sell) and `:379` (buy). Each takes `forUpdate()` on the day's counter row, but on the first sale or purchase of the day **that row does not exist yet, so there is nothing to lock**. Parallel requests all read zero, all price at the full rate or pass the stock limit, then all upsert. The sell side bypasses the step-down; the buy side buys a merchant's limited daily line several times over.
**Fix:** lock the player row first (`trx('players').where({ id }).forUpdate()`), which serialises all of one player's marketplace activity. Or insert the counter row with `ON CONFLICT DO NOTHING` before locking it.

**H8. The rate limiter can be used to lock a specific player out.**
`middleware/rateLimit.ts`. `playerKey` decodes the token **without verifying** it, so anyone can forge `{ playerId: <victim> }`, send 600 requests a minute to any `/api` path, and the victim gets 429 on everything. Separately, `clientKey` trusts `CF-Connecting-IP` unconditionally. That is only safe if Hetzner's firewall admits Cloudflare's ranges alone; if the origin is reachable directly, the header is attacker-controlled and the auth and guest limits are bypassable.
**Fix:** verify the token in `playerKey` (an HMAC check costs microseconds; fall back to the address on failure). Confirm the origin firewall, or only honour the header when `req.socket.remoteAddress` is in Cloudflare's published ranges.

**H9. NPC dialogue actions are taken from the client and never checked.**
`routes/npcs.ts:113`. `action` comes straight from the request body. It is never matched against the NPC's current dialogue options, and there is no check that the player is at the NPC's location. Any NPC can start any quest, and talk objectives can be handed in from anywhere on the island.
**Fix:** load the dialogue stage server-side (you already derive it in `resolveStage`), accept only an action present in that stage's `options`, and require `players.current_location_id === npc.location_id`.

### Medium

**M1. Mining rocks get the Woodcutting provision buff after the first swing.**
`services/gameTick.ts:1429`. The shared woodcutting/mining-rock restart branch calls `buffTimerBonus(action.player_id, 'Woodcutting')` whatever `skillName` is. A Mining provision applies to the first swing only, and a Woodcutting provision speeds up mining. Live since Cooking shipped. One-word fix: pass `skillName`.

**M2. Raw `.increment('xp')` is still in fourteen places.**
CLAUDE.md warns this silently drops XP when the `player_skills` row is missing. Sites: `gameTick.ts:522` (travel), `:663` (hunting); `mining.ts:193, 225, 309, 343`; `woodcutting.ts:234, 265`; `smithing.ts:171, 329, 426`; `carpentry.ts:213, 255`; `quests.ts:182` (inside an upsert, fine). Four of the mining and woodcutting ones pay **Exploration**; if any live player lacks an Exploration row, that XP has been evaporating. Worth running once on production:
```sql
SELECT p.id, p.username, s.name FROM players p CROSS JOIN skills s
LEFT JOIN player_skills ps ON ps.player_id = p.id AND ps.skill_id = s.id
WHERE ps.id IS NULL;
```
**Fix:** one `awardXp()` helper (see §5.3), and a backfill migration for whatever that query returns.

**M3. `resolveRecipe` has no transaction.**
`services/recipes.ts:~270`. The main crafting executor consumes inputs with absolute writes (`quantity: inv.quantity - input.qty`), then awards the output. A failure partway loses the inputs, and a concurrent storage move against the same stack is a lost update in either direction. It only runs from the tick, so the window is narrow, but it is the most-used write path in the game.

**M4. Hunting arrows are written as an absolute number.**
`services/gameTick.ts:680`. `update({ quantity: newQty })` from a stale read. A trade, drop or deposit of arrows landing in the same moment is overwritten. Use `decrement` guarded by `quantity > 0`.

**M5. Paddle integration gaps.**
`routes/paddleWebhook.ts`, `services/talers.ts`.
- **Refunds and chargebacks are ignored.** Only `transaction.completed` is handled, so someone can buy Talers, spend them on unlocks, then charge back. Handle `adjustment.created` / refund events: write a compensating negative ledger row and flag the account if that takes the balance below zero.
- **Quantity is ignored.** Only `items[0]` is credited, at one tier's worth. The client sends `quantity: 1`, but Paddle's overlay allows quantity changes unless the price is locked to 1 in the dashboard. Either lock it there or multiply by `items[0].quantity` server-side.
- **Financial records cascade-delete.** `taler_purchases` and `taler_ledger` are `ON DELETE CASCADE` from `players`, and the hourly guest sweep deletes players. A payment record should never vanish with an account; use `RESTRICT` (or `SET NULL` plus a retained username) on `taler_purchases`.
- Guests are kept out of checkout only because Paddle needs an email. The webhook should refuse to credit a guest account explicitly.

**M6. Any player can listen to any location's or region's chat.**
`index.ts:293`. `join_location` accepts whatever id the client sends and joins that location and region room. Derive the room from `players.current_location_id` server-side (and rejoin on arrival from the tick) instead.

**M7. Guests and muted players can whisper through any channel.**
`routes/chat.ts:257`. Whispers are detected by message content (`name@message`), but the guest gate checks the `channel` field and the mute exemption lets `channel: 'guild'` through. A guest can whisper anyone by posting on Help; a muted guild member can whisper anyone by posting on Guild. Parse the whisper first, then apply the guest and mute rules to the whisper as its own channel. Also: there is no ignore/block list, so whispers are an unmoderated harassment channel.

**M8. Shop buyers pay whatever the price is at the moment of purchase.**
`services/shops.ts:640`. The comment says the on-screen numbers are never trusted, which is right for quantity but means an owner can raise the price between page render and click, and the buyer pays it. Have the client send the unit price it displayed and refuse on mismatch, the way `/marketplace/sell` does with `expectedTotal`. Same for `sellToShop` with the order price.

**M9. Login reveals a ban and its reason before checking the password.**
`routes/auth.ts:150`. Anyone who knows a username learns whether that account is banned and why. Check the password first.

**M10. Two presence systems disagree.**
`connectedPlayers` in `index.ts` is a `Set` that the first closed tab empties. `lib/presence.ts` already explains why that is wrong and does it properly with room counts. Five places still read the Set: playtime tracking, the admin online list, guild online dots, "Players here", and the online count. With two tabs open, closing one stops playtime accrual and shows the player offline. Replace every read with `isPlayerOnline`.

**M11. No length limits on player-written content.**
Forum threads and replies, private messages, guild forum posts, guild descriptions and poll option counts are bounded only by Express's 100 KB body limit. At the forum limiter's 120 per minute, one account can write about 12 MB a minute of forum text. Add explicit caps (chat already has `MAX_MESSAGE_LENGTH = 500`).

**M12. Account settings are weaker than registration.**
`routes/settings.ts:47`. Password change has no minimum length and hashes at cost 10 against 12 everywhere else. Email change compares case-sensitively (registration is case-insensitive, so `Bob@` and `bob@` can coexist), validates nothing, sends no notice to the old address, and both routes throw a 500 for a guest (`bcrypt.compare` against a null hash).

**M13. The bot check is answerable by any script.**
`services/botCheck.ts`. `{ a, b }` goes out as plain JSON over the socket and in the 423 body, and the answer is `a + b`. It works as an AFK limiter and deters nobody automating the game. Any text challenge a client can read, a script can read. The durable answer for an idle game is server-side signals: action cadence that never varies, 20-hour sessions, answers arriving in under 200 ms. You already count `failed_bot_checks`; recording response latency beside it would give you the data.

**M14. The homepage promises something the server no longer does.**
`apps/client/index.html`. The meta description says work "keeps running for up to 30 minutes unattended"; the Open Graph text says it "keeps running while the tab is closed". Since `lib/presence.ts`, actions are **cancelled 90 seconds after the last socket disconnects**. Either the copy or the rule should change. That is a design call, not a code fix, and worth making deliberately given the "logged in ~8 hours a day" assumption.

**M15. Every module imports from `index.ts`, and `.env` loads by accident.**
37 route and service modules import `logger` or `io` from `../index`, while 40 import `logger` from `lib/logger`. There are two separately configured loggers. The circular import is invisible in production because `index.ts` is always the entry point, but anything else that loads a route first breaks: the audit harness failed on it with `argument handler must be a function`, because the router it imported was still `undefined` mid-cycle. Relatedly, `dotenv.config()` in `index.ts` runs *after* every import. Env vars are loaded in time only because `db/index.ts` happens to call `dotenv.config()` itself and happens to be imported before `config/jwt.ts`.
**Fix:** move `io` into `lib/io.ts` (set once at boot), import `logger` only from `lib/logger.ts`, and make `import 'dotenv/config'` the first line of `index.ts`.

**M16. Server-side dependency advisories.**
`pnpm audit --prod` reports 21 advisories (7 high). The ones that matter on the server: `engine.io` < 6.6.7 (two connection-exhaustion DoS, via `socket.io`), `qs` (three DoS, via Express), `body-parser` < 2.3.0, and `ip-address` (via `express-rate-limit`). All are patch-level bumps. The client-side ones (`react-router` RSC mode, DOMPurify config-mutation issues, `ws`) do not affect how the client uses those libraries, but bumping is free.

**M17. The repository cannot build its own database.**
A fresh `migrate:latest` fails at `20260715010528_canonicalize_huntable_animals` ("Eld Grove location not found"), because migrations depend on seed data and the seeds depend on tables that later migrations create. CLAUDE.md knows this. The long-run cost is that there is no disaster-recovery path from the repo alone, no clean test database, and every future contributor inherits the same wall.
**Fix:** squash to a baseline. Take `pg_dump --schema-only` of production plus a content-only export, commit it as `00000000000000_baseline.ts`, keep the old files for knex's bookkeeping behind a check that skips them on a fresh database, and add a CI job that builds a database from zero.

## 5. Structural recommendations

These are the long-run fixes. Each one closes a whole class of bug rather than one instance, which fits the "build for longevity" rule better than patching route by route.

### 5.1 One inventory module, like `gold.ts`
`services/gold.ts` is why gold has no dupe: every movement goes through four functions, each locks, each refuses rather than clamps, and `reconcileGold()` proves it. Items deserve the same.

- `takeItemsWithin(trx, playerId, itemId, qty)` as a single conditional statement: `UPDATE player_inventory SET quantity = quantity - $1 WHERE player_id = $2 AND item_id = $3 AND quantity >= $1 RETURNING quantity`, then delete the row if it reached zero. It returns false on no match. That one statement cannot race.
- `giveItemsWithin(trx, …)` as `INSERT … ON CONFLICT (player_id, item_id) DO UPDATE SET quantity = player_inventory.quantity + EXCLUDED.quantity`.
- The same pair for `property_storage`, `shop_listings` and `ground_items`.
- **Database backstops:** `CHECK (quantity > 0)` on `player_inventory`, `property_storage`, `shop_listings`, `ground_items` and `trade_offers`, and `CHECK (gold >= 0)` on `players`. There are **no CHECK constraints anywhere in the schema today.** With them, any future bug of this class fails loudly instead of minting items.
- A grep-able rule for CLAUDE.md: no file outside the inventory module writes `player_inventory` directly.

`removeItemFromInventoryWithin` and `addItemToInventoryWithin` in `services/inventory.ts` are already most of the way there. Twenty-odd call sites write the table directly today.

### 5.2 An action-handler registry for the tick
`gameTick.ts` is 1,493 lines of one function branching per action type. CLAUDE.md's thirteen-item checklist for new action types exists because of that shape: every skill re-implements restart, the limiter, xpInfo, drops and failure handling, and every new skill forgets one. Replace the branches with a handler per type:

```ts
interface ActionHandler {
  resolve(trx, action): Promise<ActionResult>;       // grants, inside one transaction
  canRepeat(trx, action, result): Promise<boolean>;  // re-validate tools, inputs, flags
  nextTimer(action, result): Promise<number>;
  skillName(action, result): string;
}
```
The tick then does claim → resolve → repeat-or-delete → limiter → xpInfo → emit **once**, for every type. Checklist items 1, 5, 11 and most of 7 and 9 become impossible to get wrong. It also puts each resolve inside one transaction, which fixes M3 and M4 for free. This is the largest item here and best done a few handlers at a time behind the H2 claim step.

### 5.3 `awardXp(trx, playerId, skillName, amount)`

### 5.4 Session versioning
`token_version` from H1. One column, one comparison, and bans, resets and "log out everywhere" all start to mean what they say.

### 5.5 A regression harness for races
The harness behind the **[PROVEN]** findings is about eighty lines: build a scratch schema, mount the real routers, fire N parallel requests, and assert that the total count of an item across pack, storage, ground and worn slots is unchanged. Committed as `scripts/raceCheck.ts` and run before deploys alongside `items:audit`, it turns this class of bug from "found by an audit" into "fails the check".

## 16. M5 Paddle (2026-09-26)

`routes/paddleWebhook.ts`, `services/talers.ts`, `services/guest.ts`, migration `20260926010000_taler_refunds`. Webhook shapes taken from Paddle's own schema (`adjustment.created`: `action`, `type`, `status`, `transaction_id`, `totals.subtotal`, `currency_code`; `transaction.completed`: `items[].price.id`, `items[].quantity`, `details.totals.subtotal`).

- **Quantity:** every item is credited at its tier times its quantity; any unknown price or bad quantity credits nothing (logged, 200).
- **Guests and missing players:** refused, logged for a manual refund, 200 (a missing player used to 500 on the foreign key, so Paddle retried forever).
- **Refunds and chargebacks:** an APPROVED `refund`, `credit`, `chargeback` or `chargeback_warning` takes back the share it covers (all for `full`; `talers x adjusted subtotal / purchase subtotal` in the transaction's own currency for `partial`); `*_reverse` restores it. Once per adjustment id (`taler_adjustments`), net held between zero and what the purchase credited. A partial that cannot be priced (pre-migration purchase, or a currency mismatch) is recorded `needs_review` with nothing moved. Pending refunds wait for their `adjustment.updated`. An adjustment for a transaction not yet recorded answers 500 so Paddle retries.
- **Money records outlive accounts:** `taler_purchases` and `taler_ledger` are now `ON DELETE RESTRICT` (were CASCADE); the guest sweep skips and logs any guest holding Taler records instead of failing.
- Two concurrency fixes found while proving it: `creditPurchase` is insert-or-ignore (it was check-then-insert, so simultaneous copies of one webhook could 500), and `applyPaddleAdjustment` takes the purchase lock before its duplicate check (the other way round, 4 of 5 simultaneous copies of one refund threw).

**Proven:** 24 signed-webhook proofs through the real app on `main`'s schema plus the migration, all pass; against the pre-fix code 14 of them fail (quantity 3 credited 500; a guest credited; a missing player a 500; refunds and chargebacks ignored; the sweep and a direct delete took purchase records with the account). `race:check` gains two money scenarios (19 total, all hold): one refund delivered five times at once (pre-fix ordering: 4 of 5 copies threw), and five 200-Taler spends racing a chargeback on a 500 balance (locks removed on purpose: 4 to 5 spends went through). Migration applies on `main`'s schema, `down()` restores CASCADE, reapplies cleanly.

**Dashboard, optional:** locking each Taler price's quantity to 1 in Paddle keeps the checkout simple; the server no longer depends on it.
